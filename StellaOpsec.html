Collect security findings into a reviewable report

StellaOpsec is a modular PowerShell toolkit for collecting selected Windows, network, web, identity, event-log, and cloud configuration data. It organizes those observations into structured reports so an assessor can review what the available evidence does and does not establish.

scope note

The public portfolio describes assessment areas and verification boundaries without publishing sensitive operational details. The project is a dormant prototype, not a currently offered security service or a comprehensive scanner.

overview

Security reviews often require information from several places: host configuration, network services, web response settings, identity systems, event logs, and cloud resource policies. Collecting these observations through separate scripts can make it harder to compare results or prepare a consistent handoff.

StellaOpsec explores a modular collection-and-reporting workflow. Individual modules gather selected configuration data, shared objects organize the results, and reporting utilities can produce HTML, JSON, CSV, and Excel outputs for human review.

why this matters

The practical goal is to make collected evidence easier to inspect and communicate. A structured report can help an assessor separate observed configuration from assumptions, identify gaps that need follow-up, and explain which checks were limited by permissions, dependencies, or missing data.

For a small team, the value is a repeatable starting point for selected checks and a more consistent reporting format. It does not replace expert interpretation, a full penetration test, or a dedicated cloud-security posture platform.

what it does
  • Hardware identity layerRandomizes registry-exposed hardware strings - GPU descriptor, hardware profile GUID, simulated install date - that fingerprinting services commonly check as VM tells.
  • Network layerPairs VM-level network isolation with a proxy chain and an independently-verified kill switch, so a VPN/proxy failure can never leak the operator's real egress path mid-engagement.
  • Fail-loud audit scriptA standalone PowerShell verification pass checks the environment against ~10 known fingerprinting vectors before it's used operationally - MAC OUI against known hypervisor prefixes, GPU descriptor, install-date age, DNS leak test, kill-switch test - and refuses to give a quiet pass; anything unconfirmed halts with an explicit [CRITICAL].
verification logic

The audit is the deliverable, not the evasion

The key design principle is to distinguish an observation from a conclusion. A reachable port does not prove a service is vulnerable, a public-looking policy entry does not alone establish effective exposure, and an inventory result does not prove that a security control is working end to end.

fingerprint verification (illustrative excerpt)
$vmwareOUIs = @('000C29', '000569', '001C14', '005056') if ($vmwareOUIs -contains $oui) { $macStatus = 'FAIL - VMware OUI detected'; $flags += 'MAC' } if ($gpuDesc -like '*VMware*' -or $gpuDesc -like '*SVGA*') { $gpuStatus = 'FAIL - VMware GPU exposed'; $flags += 'GPU' } # ... network egress, DNS leak, kill-switch, and install-age checks # follow the same pattern: verify with evidence, or flag and halt.

Assessment results can be incomplete when commands fail, required modules are missing, permissions are insufficient, or source data is unavailable. A dependable next version should represent each check as successful, failed, or incomplete, preserve relevant error context, and avoid presenting missing evidence as a clean result.

engagement notes

Status: prototype / dormant. The inspected source contains modules for Windows host inventory, network and web checks, credential-related configuration, event-log review, Active Directory, selected Google Cloud and Azure settings, finding generation, and report export. This does not establish broad environment coverage or successful end-to-end execution.

same discipline, different domain

The next engineering priorities are safer CLI argument handling, accurate interpretation of configuration fields, PowerShell-version compatibility, explicit partial-failure states, and repeatable tests against representative systems. The emphasis is on making the existing checks more precise and dependable, not overstating what they prove.
