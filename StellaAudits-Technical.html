StellaAudits: Automated Website Audit and Reporting Platform

A locally operated auditing application that brings website checks, severity scoring, historical comparisons, PDF reporting, and human-reviewed outreach into one repeatable workflow. This page documents the implementation and its limits for technical readers.

01 / overview

StellaAudits retrieves a supplied website, runs a collection of accessibility, search-engine optimization, local visibility, and passive security checks, then turns the results into a scored report. Each finding can carry a category, severity, explanation, business relevance, recommended action, reference, and supporting evidence.

The same workflow records audit history, compares later runs, tracks lead status, and prepares a personalized outreach draft. The central design goal is to make automated checks useful in a small service workflow without removing human review from commercial outreach.

Scope note: this is a working MVP, not a certification service. A generated score summarizes the checks that ran. It does not prove legal compliance, complete accessibility, security, search performance, or business results.

02 / audit pipeline

Orchestration and shared findings

The runner coordinates specialized modules and normalizes their output into a shared finding model. That separation lets detection code focus on evidence while scoring, persistence, and report generation operate on a consistent structure.

01 / FETCH

Retrieve the target URL and parse the initial HTML response.

02 / INSPECT

Run accessibility, SEO, local SEO, and passive security checks.

03 / CROSS-CHECK

Use optional PageSpeed and Lighthouse data when external access succeeds.

04 / NORMALIZE

Collect findings, evidence, severity, and remediation guidance.

05 / SCORE & SAVE

Calculate the score and retain an audit summary plus finding snapshot.

06 / DELIVER

Render a PDF and make the result available through the local interface.

03 / accessibility

Static checks inspect common accessibility-related HTML structures, including image alternative text, form labels, document language and title, heading hierarchy, unnamed links, duplicate IDs, table-header structure, and embedded-frame titles.

When PageSpeed integration is available, Lighthouse can add browser-rendered findings such as color contrast and other structural issues. Findings are organized around relevant WCAG criteria and include explanations and suggested fixes where supported.

Limit: automated checks cannot independently establish ADA compliance or replace keyboard testing, assistive-technology testing, and manual accessibility review.

04 / search visibility

SEO and local SEO

SEO checks examine page titles, meta descriptions, primary headings, image alt text, canonical declarations, mobile viewport configuration, structured-data presence, HTTPS usage, basic response time, and robots.txt and sitemap availability. Optional Lighthouse data adds a browser-based SEO assessment and score.

The local-search module looks for LocalBusiness structured data, supported business name, address and telephone fields, opening-hours information, phone numbers in visible text, embedded Google Maps content, and favicon availability.

Limits: the application does not establish search rankings, guarantee indexing, predict ranking changes, verify real-world business details, or perform comprehensive directory comparisons. It evaluates the supplied site and selected supporting resources.

05 / security checks

The security module is passive. It inspects transport-security configuration, response headers, potential technology-version disclosure, mixed-content references, and selected insecure form conditions. Findings include evidence and remediation guidance where available.

Deliberate boundary: this is not a vulnerability scanner or penetration-testing framework. It does not perform authenticated testing or exploitation. Passing an individual check does not establish that a site is secure.

06 / rendering awareness

Some sites return an initial HTML document with little content, then populate the page after JavaScript executes. StellaAudits uses initial-page content and framework indicators to estimate when static checks may be operating on an incomplete page.

When it detects a possible blind spot, the audit can add a confidence notice and adjust selected unconfirmed structural findings. Available browser-rendered PageSpeed data can provide additional evidence.

This detector is heuristic. It does not guarantee that all affected findings are corrected or independently verified.

07 / scoring model

Findings receive severity labels and contribute fixed deductions to a bounded site-health score, which is mapped to a letter grade. Informational metadata about the audit itself is excluded from the penalty calculation.

SeverityScore deductionUse
High15 pointsHigher-priority finding under the configured model.
Medium7 pointsModerate-priority finding.
Low2 pointsLower-priority finding.
Metadata0 pointsNotices about audit coverage or confidence, not site defects.

The score is an internal prioritization and presentation mechanism, not an independently validated measure of website quality, legal exposure, security, or business performance. Its meaning depends on which checks ran and how accurate their findings are.

08 / persistence and leads

SQLite stores audit summaries and compact finding snapshots. Records can retain audit dates, domains, scores, grades, finding counts, report references, and whether an audit attempt succeeded or failed.

  • Compare recorded runs to identify resolved, newly appearing, and persistent findings.
  • Track lead states such as new, contacted, responded, client, not interested, and failed.
  • Filter lead lists, add optional notes, update statuses, and retrieve generated reports or outreach drafts.

Comparisons depend on the available history and stable finding identifiers. A finding disappearing from a later report does not prove the underlying issue was fully fixed.

09 / reporting and outreach

Jinja2 templates and xhtml2pdf produce downloadable reports containing the target URL, audit date, score, grade, finding totals, category sections, and recommended actions. Historical comparison information can be included when an earlier audit is available.

The outreach subsystem selects a limited set of substantive findings for a draft email and avoids using internal confidence notices as sales arguments. It does not send email automatically.

The draft includes promotional-message disclosure, sender details, and reply-based opt-out language. If the physical mailing address is missing from configuration, the application raises a warning and marks the draft do not send. This is a safeguard for one configuration requirement, not a complete legal-compliance determination. Human review remains necessary.

10 / local interface

Flask connects the audit services to a local browser interface for running audits and managing leads. The reviewed feature set includes single-URL audits, batch submissions of up to 100 URLs, sequential processing with a delay between items, batch-progress polling, lead filtering and status updates, and downloads for reports and drafts.

Batch processing continues after individual URL failures. The app binds to the loopback interface by default. Completed audit records persist in SQLite, while batch-progress state is held in memory.

This is a local single-user workflow, not an established multi-user hosted service. Authentication, deployment hardening, and persistent background-job infrastructure are not established by the reviewed implementation.

12 / integration map

The reviewed source establishes these integration paths:

  • The runner coordinates specialized detection modules and collects their findings.
  • The JavaScript-rendering detector informs confidence notices and selected severity adjustments.
  • The optional PageSpeed integration supplies browser-rendered measurements and reports whether data was obtained.
  • The shared finding model feeds scoring, report generation, and historical comparison.
  • The database stores audit summaries and finding snapshots.
  • The report generator combines results, configuration, and available historical context into a PDF.
  • The outreach generator prepares a draft from substantive findings for a person to review.
  • The Flask app connects these services to the browser interface, batch workflow, lead dashboard, and download routes.

This modular structure separates detection from presentation and record management while allowing the outputs to participate in one workflow.

13 / verification and limits

This review is based on project documentation and inspected application and audit-module source, including the runner, finding model, scoring, persistence, fetching, accessibility, SEO, local SEO, security, PageSpeed, JavaScript-rendering detection, and outreach modules.

The review verifies the described architectural relationships at source level. It does not establish comprehensive end-to-end test coverage, production reliability, accuracy for every generated finding, or commercial results. Automated checks can produce false positives and miss issues requiring browser interaction or human judgment. External PageSpeed measurements depend on API access.

Summary: StellaAudits is a working MVP that connects automated website checks to scoring, history, PDF reporting, lead tracking, and human-reviewed outreach. Its value is the repeatable workflow. Its reports remain bounded by detection coverage and require review before being treated as evidence of remediation or compliance.
