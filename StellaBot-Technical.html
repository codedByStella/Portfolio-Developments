01 / overview

StellaBot is a personal AI desktop companion designed around continuity rather than isolated chat turns. It combines persistent memory, relationship and preference modeling, desktop activity signals, visual context, language-model orchestration, speech output, and proactive interaction routines.

The application connects these subsystems through context-building and conversation workflows. SQLite stores persistent memory, while JSON files hold several categories of runtime state and profile information. The project is under active development; inference costs and available hardware constrain sustained operation and comprehensive testing.

Scope note: this review describes components and relationships found through source inspection and a static call graph. It does not independently verify every behavior, runtime reliability, or complete end-to-end coverage.

02 / persistent memory

The memory layer includes initialization, retrieval and storage, memory-selection logic, relationship-history tracking, significant-moment recording, preference learning, companion self-memory, belief extraction, and retrieval of contextual information for model requests.

SQLite provides a persistent database for memory, while JSON supports profile and runtime state. The purpose is to retain selected context across application sessions and make relevant information available during later conversations. The presence of memory-selection logic does not guarantee that every important detail will be saved or that every retrieved detail will be relevant.

03 / relationship and identity context

Dedicated routines maintain relationship moments, learned preferences, self-memory, self-belief extraction, social-thread tracking, conversational rhythm, and companionship context. The context builder can combine this information with other memory and state sources before a model request.

This is application-level personalization: stored records and retrieval logic influence the context presented to the language model. It should not be interpreted as evidence that the model has human-like feelings, persistent subjective experience, or an independently verified internal identity.

04 / desktop awareness

Windows integration includes foreground-window detection, idle-time detection, attention classification, state updates, situational-context construction, and background capture or initiative loops. These signals give the application a way to consider desktop activity in addition to the latest chat message.

Foreground-window and idle signals are contextual inputs, not a complete understanding of user intent. Their reliability depends on the implementation, available permissions, timing, and the range of application states encountered.

05 / visual context

The visual subsystem includes screenshot acquisition, image decoding and encoding, hashing, visual-frame recording, visual-reel capture, snapshot management, storyboard construction, and textual visual-timeline generation. The conversation workflow invokes storyboard and timeline processing and records visual frames.

This creates a path for visual desktop context to contribute to a conversation. It does not by itself establish the accuracy of any interpretation made from a screenshot or prove that all capture and retrieval scenarios have been tested.

06 / model orchestration

The conversation engine prepares context from memory, relationship and preference systems, state, and companion-identity information. It coordinates model requests, recent conversation history, retries and cancellation, response extraction and cleanup, state updates, memory handling, and exchange recording.

Supporting routines include similarity checks for repetitive openings, potential information-leak detection, and diagnostic logging. These should be understood as implemented safeguards and heuristics, not guarantees that repetition or information leakage will always be detected.

07 / speech synthesis

The application has a general speech-dispatch layer, a Kokoro-specific synthesis routine, model-probing utilities, and local ONNX speech-model assets with configuration. This allows speech output to be handled as a distinct subsystem from conversation generation.

The model assets are runtime resources rather than authored source code. Their presence does not establish synthesis latency, audio quality, or compatibility across hardware configurations.

08 / proactive initiative

The initiative system coordinates idle detection, scheduling, state resets after activity, screenshot and visual-reel checks, application status, and proactive conversational turns. Its goal is to allow an interaction to begin without requiring every turn to start with a new user message.

The implementation includes a cap on unanswered autonomous messages and backoff behavior intended to reduce repeated interruptions when the user does not respond. The existence of these controls does not establish that every timing edge case or interruption pattern has been validated in real-world use.

09 / interface and diagnostics

Tkinter supplies the desktop interface. Windows APIs support selected desktop-awareness functions, and Pillow handles image operations. Diagnostic logging records application events, exceptions, response information, and state changes to aid troubleshooting across the connected subsystems.

Logging can make failures easier to investigate, but it does not replace structured health checks, recovery testing, or a verified deployment and update process.

10 / subsystem integration
  • Context building: combines memory, relationship, preference, state, and companion-identity information.
  • Conversation flow: links model requests with visual processing, state inference, memory operations, and exchange recording.
  • Visual capture: connects screenshot acquisition to frame recording and image processing.
  • Initiative: coordinates idle detection, scheduling, visual-reel state, and conversational turns.
  • Speech: routes general speech requests to the Kokoro synthesis path.

These connections are based on the inspected static call graph. They demonstrate structural integration, but do not prove that every path completes successfully under all runtime conditions.

11 / development constraints

The project is actively developed, but sustained operation and broad end-to-end verification are constrained in part by model-inference costs and the hardware available for local execution. This affects how continuously the system can be run and tested; it does not mean development has stopped.

The source inventory reports 4,348 lines across the project directory, excluding historical backups, environment directories, runtime state, logs, and model weights. The line count measures source volume, not product maturity or reliability.

12 / engineering priorities

Useful next steps include clearer boundaries for desktop capture and retained visual context, repeatable tests for memory selection and retrieval, checks for incorrect or stale context, and explicit handling of interrupted model or speech operations. Testing should also cover initiative backoff, cancellation, and state consistency across restarts.

These are sensible validation priorities for a system with several persistent and background subsystems. They are not claims that the current implementation already provides comprehensive guarantees in these areas.
