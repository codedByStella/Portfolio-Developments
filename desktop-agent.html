● ONLINE — Local System Agent

Autonomous Desktop Agent & Context-Aware State Machine

A localized, multi-threaded AI agent that operates natively on the host OS. It tracks foreground window activity via Win32 API hooks, maintains short-term visual context, and initiates autonomous interactions based on idle thresholds. Implements strict API retry logic, local SQLite state persistence, and a persistent TTS subprocess worker.

Python Win32 API (ctypes) Multi-threading SQLite PowerShell (TTS)
architecture

This system is not a simple chat wrapper. It is a background daemon designed to monitor, evaluate, and interact with the local environment without blocking the main thread or crashing on bad data.

  • OS-level context awarenessUtilizes ctypes and the Win32 API (GetForegroundWindow, GetWindowTextW) to track the user's active application. Captures window state via ImageGrab, handles deduplication using SHA-1 hashing, and maintains a rolling context reel.
  • Asynchronous orchestrationRuns a multi-threaded architecture featuring independent loops for visual capture, idle detection, and autonomous initiative. Uses threading.Event to allow safe user-cancellation of in-flight API requests.
  • Graceful degradation & rate limitingAll external LLM calls are routed through a retry decorator that handles 429/500/503 status codes with exponential backoff. If the API drops, the system catches the exception, preserves state, and fails safely without corrupting the local database.
  • Local state persistenceMaintains conversational continuity and relationship context using a local SQLite database. Handles concurrent reads/writes safely, and utilizes JSON flat-files for tracking rapid state changes (idle timers, window transitions).
  • Persistent TTS subprocessSpawns and manages a long-running PowerShell subprocess to handle text-to-speech generation, piping Base64-encoded strings to the worker to avoid the overhead of spinning up a new process for every generated response.
the problem

Most local AI assistants are stateless: they wait for a prompt, respond, and forget. They don't know what's happening on screen, they don't know if they're being ignored, and they crash if the upstream API hiccups.

The engineering challenge was building an agent that stays dormant, monitors visual context passively, and initiates interaction when appropriate — without becoming an annoying, resource-hogging monologue. That required a strict separation between "gathering context" (fast, local loops) and "generating thought" (slow, remote API calls).

engineering detail

Initiative & backoff

The agent doesn't just react; it initiates. But it has to do so gracefully. The system tracks idle time and visual-state changes — if the screen state changes and settles, the agent is allowed to evaluate whether it should speak.

To prevent the agent from talking to itself endlessly, it implements a hard cap on unanswered autonomous messages. If the user doesn't reply, the agent backs off and returns to silent observation.

conceptual logic for autonomous backoff
# Agent already tried to speak; user is busy. Go quiet. if initiative_unanswered >= INITIATIVE_MAX_UNANSWERED: continue # Visual state hasn't changed. No new reason to speak. if screen_hash == last_spoken_hash: continue # State is new and settled; ask the model if it wants to speak. reply = ask_agent(..., initiative=True) if "[QUIET]" in reply: continue

The reason this matters: an agent that can initiate but never checks whether it already tried and was ignored isn't "proactive," it's just noisy. The backoff is what keeps an always-on co-pilot from becoming something you have to mute.
