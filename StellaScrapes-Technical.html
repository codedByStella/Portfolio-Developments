01 / overview

StellaScrapes is a local public-records search and processing application. It accepts natural-language queries, resolves them against configured locations and dataset categories, retrieves records from supported Socrata sources, and prepares results for inspection or export.

The project includes a second workflow for discovering Socrata publishing domains and cataloging their datasets. That workflow helps identify candidate sources for future integration, but discovery alone does not establish that a dataset can be queried reliably by the main application.

The application is an MVP. It is not a hosted multi-user service, and the configured coverage should not be read as proof that every location and category is operational.

02 / primary search path
1. Query interpretationParse location, record type, trade terms, and date filters from a plain-English query.
↓
2. Registry resolutionMatch recognized terms and aliases to configured locations and dataset definitions, with fuzzy matching when needed.
↓
3. Supported retrievalBuild a request for the configured Socrata dataset and apply available query filters and retrieval limits.
↓
4. Normalize and filterConvert returned fields into a common result structure and apply supported date or status filters.
↓
5. Clean and exportOptionally normalize permit fields, deduplicate, prioritize records, and write CSV or Excel output.

The browser and Python entry points expose overlapping functionality, but they are not interchangeable. The CLI also exposes discovery and catalog maintenance operations that are not fully represented in the browser interface.

03 / query interpretation

The search layer converts user-facing terms into structured parameters rather than requiring users to know each dataset's API fields. Representative query forms include:

hvac permits in seattle roofing chicago last 30 days austin foreclosures

The parser attempts to identify location, record category, trade or keyword filters, and date ranges. Recognized terms are resolved against the registry; fuzzy matching provides a fallback when a query does not exactly match a known term.

Parsing and fuzzy matching are convenience features, not guarantees of correct intent. Ambiguous terms or incomplete registry mappings can produce incorrect or empty results, so users should review the selected source and returned records.

04 / registry-driven configuration

A centralized JSON registry associates geographic entries and record categories with source domains, dataset identifiers, candidate field mappings, update metadata, and optional filters.

Both search paths use registry-driven configuration to avoid writing a separate search implementation for each dataset. This reduces duplication, but adding a registry entry is not enough by itself: field mappings, query behavior, and the returned records still need validation.

Key distinction

Configuration describes a candidate integration. Operational support requires a working retrieval path and verified mapping for the source in question.

05 / discovery and cataloging

The Python discovery tools query the Socrata catalog, paginate through results, retrieve dataset metadata, and write catalog output for later review. Metadata includes names, descriptions, columns, update dates, and source links where available.

  • Discover domains publishing Socrata-hosted open data.
  • Catalog all discovered domains or a selected domain.
  • Classify candidate datasets using heuristics.
  • Infer possible fields for dates, addresses, descriptions, record types, contractors, and names.
  • Checkpoint catalog output and track failed domains.
  • Prepare selected datasets for import into the central registry.

A catalog-import utility maps selected domains to city or county entries and can merge missing dataset categories into the registry. Classification and field inference are heuristic, so the resulting configuration needs review before dependable retrieval.

06 / permit cleaning and prioritization

The permit-cleaning path prepares raw results for consistent review and downstream analysis. Depending on available source fields and configured rules, it can:

  • Reject records that fail basic address-quality requirements.
  • Exclude selected cancellation, demolition, and other unwanted categories.
  • Normalize addresses and supported date formats.
  • Format available telephone numbers and monetary values.
  • Deduplicate records using a configured identification key.
  • Map source columns into a standardized permit-oriented schema.
  • Assign a heuristic priority score and export the results to CSV or Excel.

The score uses selected characteristics such as estimated project value, work-description terms, and contractor availability. It is a rules-based review aid, not a validated estimate of purchase intent, conversion likelihood, or revenue. A generic cleaning path handles non-permit records with basic normalization, filtering, deduplication, and export.

07 / application interfaces

Node.js browser application

The local web application uses Express to expose search, CSV and Excel export, and browser metadata endpoints. Its front end uses standard HTML, CSS, and JavaScript. The interface provides a query input, example searches, a results table, search metadata, fuzzy-match feedback, and export controls. The number of displayed rows is capped separately from the underlying retrieval limit.

Python command-line interface

The interactive CLI provides search, configured-location inspection, domain discovery, cataloging, tests, and access to the preliminary prospecting workflow. It also supports direct search commands and standalone discovery and catalog operations.

Both interfaces are intended for local use. The project does not demonstrate a hosted service, multi-user access controls, or production-scale operations.

08 / buyer-prospecting module

A separate module was designed to create business contact lists for potential buyers of public-records-derived lead lists. Its workflow supports configurable city and state inputs, twelve predefined business categories, optional category and page limits, HTML parsing for business names, phone numbers and addresses, and CSV or formatted Excel exports. It can also save raw HTML responses for troubleshooting.

Parked, not operational

Project documentation records that the target business directory blocked requests during checks in July 2026. The module cannot currently be relied upon to produce usable prospect lists. Replacing the source and validating an appropriate collection method are separate work items, not completed features.

10 / verification and testing

The repository includes separate JavaScript and Python test scripts. Previously recorded JavaScript results reported 37 passing checks covering areas such as parsing, registry behavior, error handling, and live API paths. The Python script previously reported 43 passes and three warnings; it is a standalone script rather than a conventional test module discovered by the standard unittest runner.

These are historical results, not a fresh test execution for this review. They provide evidence that selected components and paths were checked, but they do not establish exhaustive test coverage, continuous upstream API availability, or end-to-end reliability for every registered location and category.

12 / development and commercialization

The implemented foundation combines registry-driven public-records search, dataset discovery, permit normalization, heuristic prioritization, and export workflows. The next major milestone is commercial validation, not a claim that a complete commercial platform already exists.

Further work on coverage, source reliability, and buyer acquisition should be weighed against demonstrated demand. The prospecting module remains parked, and the current application should be described as a functional, extensible MVP rather than an automated lead-generation business.
